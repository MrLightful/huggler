---
title: Durability and recovery
description: Understand what survives a restart and where provider delivery can become uncertain.
---

## One database, one owner

A runtime owns its SQLite file until shutdown finishes. Use `huggler.close().await` in Rust or `await host.close()` in TypeScript. Close stops intake, waits for managed work and releases the state lock. Another host using a compatible core revision can then reopen the same database to recover thread identities, history, queue state, and receipts. A concurrent open can return Rust’s `Error::AlreadyOpen` or the SDK error code `already_open`.

The default database is `huggler.sqlite3` under Rust’s `state_dir` or TypeScript’s `stateDir`. To override it, use `storage.database_path` in Rust or `storage.databasePath` in TypeScript. Both accept an absolute path or a path relative to the state directory. The runtime lock and SQLite sidecars sit alongside the database. Worktree reservations record absolute paths, so changing the configured root only affects future reservations.

## Acceptance and delivery happen separately

A host command commits a receipt and its local effects together. Retry with the original command ID, thread and payload to recover the receipt. Reusing the ID for a different intent returns Rust’s `Error::Conflict` or the SDK error code `conflict`.

The provider runs after the local commit. A host send that was committed and never claimed can reopen as failed and unsent. If the process dies after provider I/O, the restored run can report uncertain delivery. Inspect the stored run before submitting a replacement. An identical command retry returns the receipt without sending a second prompt. Durable queued work and delegated results have their own recovery paths.

## Recover a view from its cursor

For a new view, subscribe and start applying events to the returned snapshot. To resume a saved view, pass its last processed cursor and apply subsequent events to that saved view. The snapshot returned with a replay already includes changes through its current cursor.

| Operation | Rust | TypeScript |
| --- | --- | --- |
| Start a new view | `subscribe(&thread, None)` | `await host.subscribe(thread)` |
| Resume a saved view | `subscribe(&thread, Some(cursor))` | `await host.subscribe(thread, { after: cursor })` |
| Handle an expired cursor | `Error::CursorExpired` | `HugglerError.code === "cursor_expired"` |

Persist each processed event’s `sequence` with the view. The SDK returns it as a string. Use `eventCursor(savedString)` when loading it from storage. If retention has removed the required events, start a new view. History pagination and command output use their own cursors.

## Keep the native session binding

A Huggler thread has an application-owned `ThreadId` and may have a provider-owned `NativeThreadId` after its first turn. A run can likewise carry a `NativeTurnId`. Huggler uses the original provider instance to load or resume its native session where supported. A portable fork or file import supplies a bounded history prefix for a new session.
